# Trigram 索引架构与生命周期

在 dowse 中注册的每一个代码仓库都会获得专属的 [tgrep](https://github.com/microsoft/tgrep) Trigram（三元语法）倒排索引。该索引能够在从物理磁盘读取任何文件正文之前，将候选文件集合精确缩减至仅有可能命中查询的极小范围（详见 [搜索底层执行流水线](search.md#搜索底层执行流水线)）。

## Trigram 倒排索引工作原理

所谓 **Trigram**，是指从文本中按 3 个连续字符滑动提取的字串切片（例如词项 `config` 可以切分为 `con`、`onf`、`nfi`、`fig`）。Trigram 索引维护了一张倒排表，记录了包含各个 Trigram 的全部文件 ID 列表（Posting Lists）：

1. 当用户输入查询时，编译器会提取字面量词项与正则表达式模式中必须出现的 Trigram 切片。
2. 索引对 `AND` 连接的词项对应的文件列表求交集，对 `OR` 连接的词项求并集。
3. 99% 以上不匹配的文件在这一阶段被直接排除，完全无需产生任何磁盘读 I/O。

## 与 tgrep CLI 命令行无缝兼容

默认情况下，每个仓库的索引文件存放在其根目录下的 `.tgrep/` 目录中，其存储结构与微软开源的 `tgrep index` 和 `tgrep serve` 工具保持 100% 一致。

- **后台渐进式构建**：刚添加到 dowse 中的无索引仓库会被加入后台构建队列（同一时刻单线程构建一个仓库，防止打满 CPU）。在索引完全建好之前，针对该仓库的查询会自动退化为常规逐文件扫描。
- **误删自动恢复感知**：若索引目录在 dowse 运行期间被意外清除（例如执行了深度清理命令 `git clean -fdx`），后台文件监听器会在数秒内察觉并自动将该仓库重新加入索引构建队列。

## 索引存放位置策略

虽然默认将 `.tgrep/` 保存在仓库工作区内部最为直观，但对于经常需要彻底清理构建产物或对 Git 工作区有严格洁癖的开发者，dowse 允许将索引统一剥离至外部集中目录。

### 通过命令行配置

```bash
# 全局默认：所有未单独指定的仓库统一将索引保存在外部目录
dowse settings set index.location external

# 自定义外部集中存储目录（默认为操作系统的用户数据目录）
dowse settings set index.external-dir D:/dowse-indexes

# 单独为特定仓库设置例外，保留在仓库自身 .tgrep/ 目录下
dowse repos index-location api --repo

# 输出纯路径文本，供 tgrep 命令行直接调用
tgrep search foo --index-path "$(dowse repos index-location api -q)"
```

### 存储迁移机制

- 当修改某个仓库的索引存储位置时，dowse 会在磁盘上直接移动现有索引文件，而非重新构建。若跨文件系统移动受限，原文件会保留并在目标位置启动新建。
- 当某个仓库被从应用中删除或在磁盘上被移动，其遗留在外部集中目录中的孤立索引文件会被系统自动识别并清理。

## 基于文件监听器的实时保鲜机制

在两次索引构建之间，dowse 通过操作系统级的文件系统监听器（File Watcher）实现检索的毫秒级保鲜：

- **活动文件监听器**：为每个仓库维护专属监听器，实时捕获自上一次索引序列化以来的所有文件创建、修改和删除事件。
- **脏文件集合实时合并**：在执行检索时，所有被标记为近期修改或新增的文件会自动并入候选文件集，并直接从磁盘读取最新内容。无论是在镜像仓库刚刚完成了 `git pull`，还是在外部编辑器刚刚按下了保存，修改均可在瞬间被检索命中。
- **离线变更冷启动对比**：当 dowse 启动时，它会将文件系统的最新修改时间戳与索引记录的生成时间戳进行快速比对，自动侦测在 dowse 关闭期间发生的离线改动、文件重命名或删除。

## 增量更新机制与自动触发条件

当需要同步索引时，无需耗费时间重编整个代码库：

- **流式合并（Streamed Merging）**：增量更新仅重编监听器识别到的脏文件，将其切片后流式写入现有索引副本，而未发生变化的海量 posting 列表则以块拷贝形式直接复制。
- **自动触发阈值**：当某个仓库累积的文件变更达到 **500 次** 时，系统会自动在后台触发一次增量更新。
- **手动触发快捷方式**：
  - `Ctrl+Shift+R`（macOS 为 `Cmd+Shift+R`）：增量更新当前范围内的全部仓库索引。
  - `dowse index [--wait]`：从终端一键更新在范围内的索引。
  - `dowse index --full`：强制对全量文件从头开始彻底重建。
- **全量重建场景**：全量重建仅在索引缺失、元数据读取损坏、绝大部分文件发生剧烈变动或用户显式要求时执行。

---

## 暂存区机制与不间断检索保障

所有的增量更新与全量重建均在一个完全隔离的临时暂存目录（Staging Directory）中进行：

- 在后台构建或更新索引的过程中，用户在前端执行的任何搜索查询均不受任何文件锁阻碍，持续可用。
- 只有在新索引完整生成并校验无误后，系统才会通过原子指针切换（Atomic Swap）无缝替换内存中的 Reader 及磁盘目录。

## 性能基准数据

以下为包含 245,000 个源码文件、索引体积 1.7 GB 的大型代码仓库实测数据：

| 操作类型         | 耗时       | 备注                                       |
| ---------------- | ---------- | ------------------------------------------ |
| 首次全量索引构建 | 约 9 分钟  | 完整遍历每个文件，生成全量 Trigram 倒排表  |
| 增量索引更新     | 约 10 秒   | 仅扫描重编修改文件，将切片流式并入现有索引 |
| 索引时效性校验   | 约 3 秒    | 极速比对文件修改时间戳与索引元数据表       |
| 交互式搜索延迟   | 20–60 毫秒 | 内存热索引状态下跨多仓库端到端响应时间     |
